// GAME TECHNOLOGY / PUBLIC ALPHA

Tatuy.

I wanted to write games in Python and still understand what the engine does.

Tatuy is an experimental 2D engine built around scenes, an entity-component system, explicit update phases, and a rendering boundary that does not require game logic to know how pixels reach the screen.

// 01 — MOTIVATION

Make the moving parts visible.

Game development becomes much easier to reason about when you can answer a few ordinary questions: Which system runs first? When does a spawned entity become visible? What does rendering own, and what does the game own?

Tatuy is my way of exploring those questions without giving up Python for gameplay. The engine makes frame execution explicit and keeps reusable mechanics separate from individual game rules.

// 02 — HOW IT IS ORGANIZED

Separate the jobs. Keep the flow readable.

The design puts game code at the top, presentation intent in the middle, and platform drawing behind a boundary.

EXECUTION

An explicit frame lifecycle

Control and simulation stages have defined ordering, with commit points for structural world changes before presentation. That makes frame behavior easier to inspect than a collection of hidden callbacks.

Frame lifecycle documentation ↗

PRESENTATION

Ask for a drawing, not a backend call

Scenes and features submit semantic operations—shapes, text and textures—to a render queue. The pipeline orders them by layer, depth and insertion sequence before backend execution.

// 03 — A REAL EXAMPLE

Growing a tree to test the engine.

The Procedural Tree experiment uses a seeded generator to build branch and foliage geometry. Its growth state changes over time, while a separate renderer presents that state through Tatuy's render queue.

It is intentionally adjustable: regenerate a seed, restart growth, toggle foliage, pause, or change branch depth. That turns a small visual experiment into a test of input, simulation, and presentation working together.

// 04 — TRADEOFFS & LIMITS

Optimize when the evidence asks for it.

WHAT EXISTS

Python engine, Pygame backend, experiments

The codebase has scenes, systems, ECS composition, render operations, reusable features, and example games. The browser showcase has a build pipeline, but deployment configuration is not the same as verifying every playable in a live browser.

WHAT IS NOT DONE

No native backend or performance promise

SDL2 and C++ infrastructure remain possible future directions. Tatuy is alpha software, not a completed general-purpose engine. I am using increasingly demanding experiments to find what its abstractions should become.
